Fire Handbook

Find the root cause fast: pick the angle, then pick the tool. Do not re-read code you can run. Measure it.

  1. Reproducemake it fail on demand, as small as you can
  2. Localizewhich commit, layer, data, or moment? Halve it.
  3. Observedebugger, profiler, sanitizer. Facts, not guesses.
  4. Hypothesizeone sentence that an experiment could disprove
  5. Testcheapest experiment. Change one thing.
  6. Fix at rootthe decision, not the crash line
  7. Provefailing test goes green; revert fix and it goes red
  8. Recordone paragraph in the journal

Five rules of the road

  1. Run it first. Build, run, watch what it really does.
  2. Follow the data, not the code. A watchpoint beats 100 grep hits (S7).
  3. Crash site is not bug site. Walk backwards from the bad value.
  4. No symbols, no debugger. -g first (S5).
  5. 25 minutes, no falsified hypothesis? Change angle or ask, and bring what you tried (S2).
Before you install anything at work: ask which tools are already approved. Never paste program code or logs into an AI tool that security has not approved (S14).

60-second triage

# 1 Can I make it fail on demand?   2 Copy the exact error text.
# 3 Did it ever work?  yes -> git bisect (S4)   4 Symbols? (S5)
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug \
      -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
cmake --build build -j
./build/app            # run it, see the failure

The debug loop

Use when you are thrashing: re-reading the same functions, changing three things between runs. You need a process, not another tool.

Strategy

  1. Reproduce. Fixed input, fixed seed, one thread if you can. If you cannot reproduce it, making it reproduce is the task.
  2. Localize by halving. Pick the axis that halves the search fastest (table below).
  3. Observe with a tool. Debugger state, a profile, a sanitizer report.
  4. Hypothesize in one sentence that an experiment can falsify. Good: "m_total goes negative in applyDelta because rebalance posts a delta from a stale believedTotal_." Bad: "the messaging is broken."
  5. Test cheaply. A watchpoint, a conditional break, one dprintf. Change one thing at a time.
  6. Fix at the root. Ask "why?" until the answer is a decision someone made.
  7. Prove it. Add a test that fails before and passes after. Revert the fix once and confirm the bug returns.
  8. Record it in the journal (S13).

Anti-patterns

  • Re-reading code instead of running it
  • A null check at the crash site
  • Three changes between runs
  • Trusting a confident explanation, human or AI
  • Debugging Debug when the bug is in Release (S5)
  • Writing nothing down

Stuck 25 to 30 minutes?

The number is a rule of thumb. If no hypothesis has been falsified, you are not progressing: switch angle (data, flow, history), shrink the repro, or ask. Asking is expected. Bring something to the table.

First 30 minutes in a new codebase

Use when day one on a repo, a new component, or "where do I even start?" Goal: a one-page mental map and a working debug build before you read a single function.

Strategy (talk order)

  1. Measure size and languages.
  2. Layout: README, docs/, tests/, top CMakeLists.txt.
  3. Build with -g.
  4. Run it like a user. "Sounds silly, but a high-level understanding of what your program actually does is key."
  5. Anchor on main(). It hints at the architecture: plugins? event loop? Log what happens before main (init) and after (cleanup).
  6. Find tests for your component.
  7. Read the history of your area.
  8. Journal entry #1: size, entry points, build recipe, three open questions.
Many mains is normal. OpenTTD had about 33 to 37 hits: shaders, third-party test framework, one per OS, plus the real openttd_main. A tiny main that hands off to a "real main" is a good sign.
# size and languages
cloc .                     # brew/apt install cloc
cloc --vcs=git             # tracked files only
# layout
tree -L 2 -I 'build|.git|third_party'   # ✓
find . -name CMakeLists.txt | head
# entry points: the talk's exact grep  ✓
grep -irn -I --include='*.cpp' "main()" .
rg -n --type cpp '\bmain\s*\(' .
# ...or let the debugger land there
gdb ./build/app   # (gdb) tui enable ; start ; next ; bt
lldb ./build/app  # (lldb) b main ; run ; n ; bt
# tests and history
ctest --test-dir build -N              # ✓ list, run none
git log --oneline -20 -- path/to/area  # ✓
git shortlog -sn HEAD -- path/to/area  # ✓ who knows it

Lots of CMake, Python, or shell in cloc means the build is part of the problem. Zero docs means you will lean on generated docs (S10). Other entry points to hunt: static initializers (run before main), event handlers, thread start routines, plugin register calls, subscribe calls on a message bus.

Search, navigate, history

Use when you ask "Where is it?", "Who touches it?", or "When did it change?" Text search finds spelling. It cannot tell a read from a write.

Strategy

  1. Search the visible thing first: the exact error text, log line, UI label, CLI flag. Users see strings, not identifiers.
  2. Classify hits, do not read them. Split writers from readers with a regex.
  3. Over about 20 hits? Stop. Go to the debugger (S7).
  4. Need callers? Use clangd incoming calls, not more grep.
  5. Need the "why"? Read the commit message, not just the diff.
  6. Regression? git bisect run: about 7 test runs for 100 commits.
rg with no path hangs in scripts. If stdin is not a terminal, ripgrep waits to read it. Always end with a path (. or src/). The writers regex also matches the declaration int m_total = 0;; ignore that hit.
Dynamic dispatch hides from grep. Virtual calls, callbacks, std::function, and message buses only show their truth at runtime. Break in the callee and read bt.
grep -irn -I --include='*.cpp' "main()" .   # the talk's form
rg -n --type cpp '\bmain\s*\(' .
rg -n -w m_total src/          # whole word
rg -n -C3 'applyDelta' src/    # context
rg -l 'Bus::post' src/         # files only
rg -n 'TODO|FIXME|HACK|XXX' src/
rg -n -F 'Connection refused' src/   # literal
# WRITERS of a member (textual only)
rg -n 'm_total\s*([-+*/%|&^]|<<|>>)?=[^=]' src/
rg --files . | rg -i cmake      # ALWAYS give a path (see warning)
# history: who, when, why
git log --oneline -20 -- path/
git log -S'applyDelta' --oneline   # string count changed
git log -G'm_total\s*\+=' -p       # diff matches regex
git log -L :applyDelta:src/tracker.cpp   # one function's history
git blame -L 10,30 src/tracker.cpp
git blame -w -C -C src/tracker.cpp # follow moved code
git show SHA                       # read the message!

# regression: let git find the commit.
# Keep check.sh OUTSIDE the repo.
cat > /tmp/check.sh <<'EOF'
#!/bin/sh
cmake --build build -j >/dev/null 2>&1 || exit 125  # 125 = skip
./build/app          # exit 0 good, 1-127 bad
EOF
chmod +x /tmp/check.sh
git bisect start HEAD KNOWN_GOOD_TAG
git bisect run /tmp/check.sh   # names first bad commit
git bisect reset               # ALWAYS finish with this
# semantic navigation: export real compile flags
cmake -S . -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
ln -sf build/compile_commands.json .
# editor: go to definition / find references /
# call hierarchy (incoming).  No LSP?
ctags -R --c++-kinds=+p --fields=+iaS src/  # Ctrl-] in vim

Build system and debug symbols

Use when the debugger shows ?? or <optimized out>, CMake is a maze, or "it works in release." The talk's loudest tip: build with debug information.

Two separate dials

SettingMeaning
-g -O0Debug. Easiest to debug.
-g -O2RelWithDebInfo. Ship-like plus symbols. Use when the bug only shows in release.
-O2Release. No symbols. assert compiled out (-DNDEBUG).
-g -OgOptimized but debuggable. A good middle.
"Works in release" proof (run on the sandbox). Debug build: Assertion failed, exit 134. Release build: total = -10, exit 0. The bug is still there; the assert was compiled out. A green Release build proves nothing if the check was an assert.

Strategy

  1. Debug info is separate from optimization. Add -g to the build you ship, if that is the one that fails.
  2. Make the compiler tell you its real command (--verbose), not what you think the CMake says.
  3. 3rd-party libraries must also be built with symbols, or you see assembly when you step into them.
  4. One build directory per configuration: build/, build-rel/, build-asan/.
  5. Write the working build recipe in the journal the first time it works.
# configure + build with symbols and a compile database
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug \
      -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
cmake --build build -j
# SEE the real compiler command (flags, -g, -O, -D)
cmake --build build --verbose
# what is this configured with?
cmake -LAH -N build | less
grep -E 'CMAKE_BUILD_TYPE|CXX_FLAGS' build/CMakeCache.txt
cmake --build build --target help     # what can I build?
cmake --build build --target app -j   # one target
# map of the maze: target dependency graph
cmake --graphviz=build/deps.dot build       # writes deps.dot
dot -Tsvg build/deps.dot -o build/deps.svg   # needs graphviz installed
cmake -S . -B build-rwdi -DCMAKE_BUILD_TYPE=RelWithDebInfo
cmake -S . -B build --trace-expand --trace-source=CMakeLists.txt
cmake --build build --config Debug   # multi-config generators
cmake -S . -B build -G Ninja         # faster builds
cmake -DCMAKE_CXX_COMPILER_LAUNCHER=ccache -S . -B build

Do I really have symbols?

dsymutil build/app && dwarfdump --debug-info build/app.dSYM | head  # macOS ✓
# (dwarfdump on the bare macOS binary prints nothing: info lives in .dSYM)
file build/app          # Linux: "with debug_info, not stripped"

Strategy

  1. start to land at the entry point; step with n to see what happens before the real work. Use s into the "real main".
  2. Attach to skip startup and dive in after something interesting happened. Needs sudo (or ptrace permission).
  3. finish gets you out of library code you do not own.
  4. Climb to the first frame in your code and print there.
  5. ptype once you find an object: see the struct.
  6. Use set var / return to falsify a hypothesis in seconds. These are experiments, not fixes.
Scope trap. LLDB conditions run in the frame that stopped. A name from main is "undeclared" inside another method. Use this->m_total or a raw address. (Found while testing.)

Follow the data

Use when one variable shows up 100 times across methods, pointers, and a message queue. This is the sheet for your Raytheon problem. Do not read the code. Watch the memory.

The idea

A hardware watchpoint makes the CPU stop the instant one address is written. It does not care which of the 100 textual occurrences did it, or whether it went through a pointer, a reference, memcpy, or a message handler. The backtrace at that stop is the answer to "who touched it?"

Strategy: six steps

  1. Get the live object (an address, not a name). Break after construction; p obj, p &obj.field, ptype obj.
  2. Watch it with a condition so you only stop on the bad write.
  3. Read the stop. Frame 0 is the writer; the arguments show the wrong value; the stack shows the path.
  4. Hit a queue? After it, bt shows who delivered, not who sent. Move the breakpoint to the producer (post / send / enqueue / emit) and filter on the bad payload.
  5. Which write was first? Record and reverse-continue (S8).
  6. Many hits, no need to stop? Attach commands to log each write plus bt 3, then grep the log.
Rule: break at the producer, not the consumer. Filter on the bad payload. In the sandbox this one breakpoint lands in Controller::rebalance, the planted bug, without reading it.
Hardware limits. Typically 4 watchpoints, each up to 8 bytes (LLDB here: "supported hardware watchpoints: 4"). A watched local ends when its frame returns. A software fallback is very slow: watch one int, not a struct.
# GDB: -l watches the ADDRESS (survives scope change)
(gdb) break main.cpp:17        # object exists, bug not yet
(gdb) run
(gdb) p tracker  ;  ptype tracker  ;  p &tracker.m_total
(gdb) watch -l tracker.m_total
(gdb) watch -l tracker.m_total if tracker.m_total < 0
(gdb) rwatch -l tracker.m_total   # who READS it
(gdb) awatch -l tracker.m_total   # reads or writes
(gdb) continue
(gdb) break Bus::post if m.value < 0   # catch the sender
(gdb) break Tracker::applyDelta if this->m_id == 7

# or *(int*)0xADDR instead of a local's name

Time-travel debugging

Use when you ask "how did I get here?" or "who wrote this value last?" Record the run, then step and continue backwards, with the whole program state unwound.

Strategy

  1. Bad value found? watch -l it, then reverse-continue. It stops at the previous write.
  2. Crash far from the cause (corruption, use-after-free)? Reverse from the crash to the corrupting write.
  3. Intermittent or race? Record the failing run once and replay it deterministically forever.
  4. Unfamiliar flow? Record one feature (a click, a request) and walk it forward and back.
  5. Third-party library? The recording shows every API call, the arguments, and the results; compare with its docs.
  6. Record late, near the bug, unless your recorder is fast.
ToolWhereNotes
GDB record fullLinuxFree. Very slow; fine for tight loops.
rrLinux x86Free. Low overhead. Needs CPU perf counters (poor in VMs).
UDB / LiveRecorderLinuxCommercial, free trial. About 1.5 to 10x slowdown. Same GDB commands.
WinDbg TTDWindowsVisual Studio ecosystem.
Apple Silicon: none of these run natively. Use a Linux box or VM. Ask what your team already has licensed.
# A) GDB built-in
(gdb) break main.cpp:17
(gdb) run
(gdb) record full               # start recording HERE
(gdb) continue                  # run until the failure
(gdb) watch -l tracker.m_total
(gdb) reverse-continue          # stops at the previous WRITE
(gdb) bt                        # the writer, as it was then
(gdb) reverse-next / reverse-step / reverse-finish
(gdb) record stop

# B) rr
rr record ./build/app --case 42
rr replay                       # then the same gdb commands
rr record --chaos ./build/app   # randomize scheduling: shakes out races

# C) UDB (the talk's tool)
nm build/app | grep MainLoop    # find the mangled symbol
live-record --record-on symbol:_Z12PostMainLoopv ./build/app
udb app-1234-DATE.undo          # replay; reverse-* available

Three recipes to memorize

1 Who wrote this value last?
  watch -l OBJ.FIELD -> reverse-continue -> bt
2 How did I get here with this argument?
  break FUNC if ARG==BAD -> continue -> up -> reverse-continue
3 Where did this pointer become null or get freed?
  watch -l PTR -> reverse-continue -> bt

Loop until captured: while rr record ./app; do :; done (stops when the failing run is recorded).

Profilers and call graphs

Use when "what actually runs when I do X?" or "where is the time going?" A profiler also draws a map of an unfamiliar program: its hot paths, its main loop, its threads.

Strategy

  1. Explore: start the app idle, start profiling, do exactly one action, stop. The report is that feature's code.
  2. Perform: profile a release-like build (RelWithDebInfo), never -O0.
  3. Sort by self time for hot loops, by inclusive for hot subsystems.
  4. A hot function is where to look, not the bug. Take its name to the debugger and set a breakpoint on it.
  5. Screenshot the call graph or flame graph into the journal.
Inlining hides functions. In a test the hot function showed up as main because it was inlined at -O1. Use -fno-inline or -O0 when you want the graph to look like the source.
perf says "restricted"? Check sysctl kernel.perf_event_paranoid. Ask IT before changing it.
# perf (Linux): the talk's commands
sudo perf record -g ./build/app
sudo perf report

Structure, docs, dependencies

Use when you need a map (classes, libraries, includes), you hit "undefined reference", or a library you do not own misbehaves. No docs? Generate them.

Strategy

  1. Generate docs with Doxygen. Seeing the same code drawn differently builds a mental model.
  2. Read them for conventions: return types, snake_case or camelCase, error codes or exceptions. This pays off at code review and tells you "my code or a library?"
  3. Name the pattern. A message bus is Observer / publish-subscribe: who subscribes, who posts, where is the dispatch loop?
  4. Library you do not own: (1) ask for a debug build; (2) record the run and compare API calls to the docs; (3) intercept at the boundary; (4) disassembly is a last resort.
  5. Offline docs (Zeal, Dash) beat web search: no latency, fuzzy search.

Shrink the problem

Use when the codebase is too big to hold in your head. Your task is not "understand the codebase." It is "understand this path through the codebase."

Strategy

  1. Look for a test of your component first. A passing test is a tiny, deterministic program to run under the debugger.
  2. No test? Write one that reproduces the bug. It is your repro and your regression test.
  3. Thin slice. Find the smallest existing feature that behaves like yours. Trace it once end to end. Write the six-line path in the journal.
  4. Smallest change that takes the test from red to green. Commit. Only then widen.
  5. Characterization tests before touching scary legacy code: capture what it does now, then change it knowing what you broke.
  6. Good first tasks: a labeled small issue, a compiler warning, change some text or a config value, add an item to a list. Each teaches one slice.
  7. Review your diff first: every changed line should trace to the requirement.

Minimize a repro

git bisect start BAD GOOD && git bisect run ./check.sh  # history
head -n 500 input.log > half.log && ./app half.log     # input: halve, back off
git diff --stat; git diff                              # self-review
# find tests
find . -type d \( -name test -o -name tests -o -name unittests \) -not -path './build/*'
rg -l 'TEST(_F|_P)?\(|TEST_CASE\(|BOOST_AUTO_TEST_CASE' --glob '!build*' .
rg -n 'add_test|gtest_discover_tests|enable_testing' --glob 'CMakeLists.txt' .
# CTest (all run on the sandbox)
ctest --test-dir build -N          # list only
ctest --test-dir build -R tracker -V
ctest --test-dir build --output-on-failure
ctest --test-dir build --rerun-failed --output-on-failure
# find first tasks
rg -n -i 'TODO|FIXME|XXX|HACK|later|workaround|hard-?coded' --type cpp src/
rg -n -i 'tracker' tests/            # tests mentioning MY class
git log --since=3.months --oneline -- path/ | head -30
./tests --gtest_list_tests
./tests --gtest_filter='TrackerTest.*'
./tests --gtest_filter='TrackerTest.Reset*' --gtest_repeat=100  # flaky?
./tests --list-tests ; ./tests "[tracker]"        # Catch2
gdb --args ./tests --gtest_filter='TrackerTest.Reset*'
lldb -- ./tests --gtest_filter='TrackerTest.Reset*'

Crashes, memory, hangs, races

Use when segfault, abort, garbage values, leak, freeze, or "only sometimes." Beyond the talk, but it is the next thing you will meet. Core rule: crash site is not bug site.

Triage by symptom

SymptomFirst move
SIGSEGVdebugger bt, then ASan
terminate called after throwingbt; catch throw for the origin
Garbage values, works on my machineUBSan + ASan; valgrind --track-origins=yes; -Wall -Wextra
Memory growsLeakSanitizer / leaks / valgrind
Frozen, 0% CPUattach, thread apply all bt
Frozen, 100% CPUperf top / sample, then bt
Only sometimes; changes when you add a printTSan; rr --chaos; fewer threads
Fine in Debug, broken in ReleaseUB, uninitialized var, or assert doing real work: RelWithDebInfo + sanitizers

Reading a crash

  1. Frame 0 is where it died, usually innocent. up to the first frame in your code.
  2. Print the pointer. Ask "who last set this or freed it?"
  3. Then watch -l ptr (S7), reverse-continue (S8), or ASan's "freed by thread T0 here" stack.
ulimit -c unlimited       # allow core files in THIS shell
cat /proc/sys/kernel/core_pattern
coredumpctl list ; coredumpctl gdb
gdb ./build/app core      # bt full ; thread apply all bt
# macOS crash reports: ~/Library/Logs/DiagnosticReports/
(gdb) catch throw         # lldb: breakpoint set -E cxx
# sanitizers: separate build dir. Lines marked ✓ were run:
# "heap-buffer-overflow ... WRITE of size 4 ... main leak.cpp:2"

  -DCMAKE_CXX_FLAGS="-fsanitize=address,undefined -fno-omit-frame-pointer -g"

# threads (cannot combine with ASan)

# valgrind (Linux, no rebuild)

sudo gdb -p $(pgrep -n app) -batch -ex 'thread apply all bt'

# race: make it deterministic, then loop until it fails
n=0; while ./build/app >/dev/null 2>&1; do n=$((n+1)); done

Deadlock signature: two threads each in pthread_mutex_lock/futex_wait, each holding what the other needs. Fix with lock ordering (std::scoped_lock(a, b)) or less sharing. A print "fixes" it? That is a race or UB, not a fix.

Workspace and journal

Use when you want to see more at once, or you keep re-deriving yesterday's findings. Two force multipliers from the talk: a window manager, and a greppable journal.

Strategy

  1. More pixels, more context. Ask for a big or portrait 4K monitor. Build and test are remote anyway.
  2. Split your terminal: editor, debugger, search shell, and a journal window. tmux keeps it all alive if SSH drops.
  3. Use what works for you. Do not adopt a tool because someone evangelized it.
  4. Journal as you go: lowest-friction, greppable text. Carmack's .plan files are the model.
  5. Shadow a senior for 15 minutes. Note the tools you saw.
Defense-contractor note. Keep the journal where your program approves work notes. Export-controlled or program-specific details do not go in personal cloud notes or public repos. This handbook's generic method notes are fine; code excerpts and program details are not. Ask your lead.

AI: trust, but verify

Use when an AI tool (or a confident colleague) gives you a root cause. From the talk: "It sounds authoritative. It's not. It's just good at being convincing."

First: is it allowed? Use only enterprise-licensed tools your organization has approved for this data. Program code, designs, logs, and error text may be export-controlled (ITAR/EAR) or CUI. Pasting them into a consumer chatbot can be a reportable incident. If unsure, ask security. Practise on this sandbox or open-source repos instead.

The workflow: AI proposes, debugger judges

  1. AI claims "the bug is X because Y."
  2. Turn the claim into one falsifiable experiment (below).
  3. Run it. Evidence agrees: keep it, journal it.
  4. Evidence disagrees: give the AI the evidence ("the watchpoint never fired there; the write came from frame Z") and ask for a new hypothesis.

The talk's MySQL case: the AI confidently proposed wrong root causes and a "definitive patch." Time-travel debugging constrained it by forcing it to confirm every hypothesis with evidence.

Good at / bad at

  • Good: summarizing a file, searching fast, explaining unfamiliar code, driving tools
  • Bad: knowing it is wrong, staying on track, challenging you, defending claims with evidence

Turn a claim into an experiment

AI saysRun this
"m_total goes negative in applyDelta"watch -l ... if ... < 0; does it stop there, with what v? (S7)
"Called once per frame"break Foo::tick + ignore 1 999 + info breakpoints hit count (S6, S9)
"Pointer is freed before use"ASan: does it report use-after-free, with which stacks? (S12)
"This commit introduced it"git bisect run (S4)
"These classes are not coupled"rg + clangd incoming calls + Doxygen caller graph (S10)

Prompts that work (approved tools, safe code)

Orient: "Explain the control flow from main() to
FEATURE. Cite file:line for each claim. Mark
anything inferred rather than read as INFERRED."

Evidence: "Give ONE gdb/lldb command sequence that
would prove your hypothesis wrong. No fix yet."

Constrain: "Here is the bt and watchpoint output.
Which of your hypotheses does this falsify?"

Challenge: "What is the strongest alternative
explanation I have not excluded?"

Avoid: "fix this" with no repro; accepting the first explanation of a stack trace; letting it edit code before you can reproduce the failure. Tools named in the talk: Sourcegraph, ChatDBG, Claude Code, Undo's UDB + AI prototype.
