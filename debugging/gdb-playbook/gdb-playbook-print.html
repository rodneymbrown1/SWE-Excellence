Before touching the debugger

  1. Write the symptom as one sentence with the exact text, value, or tick count you saw.
  2. List three possible causes. "Heartbeat lost" could be never generated, generated wrong, dropped in the queue, received late, rejected by the handler, or timeout set too low.
  3. Pick the observation that separates them. Which single breakpoint or watchpoint would be true under one cause and false under the others?
  4. Make one observation. Cross off causes. Repeat. If nothing got crossed off, the observation was a bad one.

Mistakes happen

Going backwards

You will type next one time too many. Plan for it. There are four levels of undo, from cheap to heavy. Pick the cheapest one that still works for your target.

1 · Free, always available

Print before you change, and let GDB remember.

(gdb) p total              # $7 = 15  (every print is saved as $N)
(gdb) set var total = 0    # experiment
(gdb) p $7                 # old value is still there
(gdb) set var total = $7   # put it back
(gdb) p $                  # last value;  $$ = the one before;  $$3 = three back
(gdb) tbreak <line> ; run # cheapest "rewind" of a short program: start over
(gdb) info breakpoints     # shows "already hit 37 times"
(gdb) ignore 1 36          # rerun, skip the first 36 hits, stop on #37

The hit-count trick is the most useful rewind on targets that cannot record. Crash on hit 37? Rerun with ignore 1 36 and you land one step before it, every time, if the run is deterministic.

2 · Checkpoint (native Linux, single thread)

(gdb) break <Function>
(gdb) run
(gdb) checkpoint            # fork a snapshot of the process here
(gdb) next                  # try something risky…
(gdb) restart 1             # …and jump back to the snapshot
(gdb) info checkpoints
(gdb) delete checkpoint 1

It forks the process, so it does not capture other threads and does not work on a remote target. Use it to try several set var experiments from the same state.

3 · Record and reverse (native, slow)

(gdb) start
(gdb) break <a few lines before the suspect area>
(gdb) continue
(gdb) record full           # recording starts HERE, not earlier
(gdb) next
(gdb) reverse-next          # undo one line
(gdb) reverse-step          # step backwards INTO the call that just returned
(gdb) reverse-finish        # run back to where this function was called
(gdb) reverse-continue      # back to the previous breakpoint or watchpoint
(gdb) reverse-stepi
(gdb) info record
(gdb) record goto begin     # also: end, or an instruction number
(gdb) record stop           # discard the history, keep the state

Turn recording on late, as close to the problem as you can. It is very slow and uses memory for every instruction. Cap it with set record full insn-number-max 200000. Some modern instructions are unsupported and GDB will say so.

4 · Full replay (rr, UDB)

$ rr record ./app <args>          # run once, any number of threads
$ rr record --chaos ./app           # randomize scheduling to expose races
$ rr replay                         # opens gdb on the recording
(rr) continue                       # runs to the crash
(rr) watch -l obj->field
(rr) reverse-continue               # stops at the last write, deterministically

rr is Linux (mostly x86) and needs access to hardware performance counters, so it often fails inside VMs. UDB is the commercial option from the talk's sponsor. On a bare-metal target, hardware trace (ETM or a probe vendor's trace tool) is the equivalent.

Don't lose it in the terminal

Capturing findings

Terminal scrollback is not evidence. Capture at three layers: the raw session, the repeatable script, and the written conclusion.

Layer 1 · Raw session

# put in ~/.gdbinit or a project investigate.gdb
set pagination off
set confirm off
set print pretty on
set print object on          # real (derived) type behind a base pointer
set print elements 200
set logging file gdb-session.log
set logging overwrite off
set logging enabled on       # GDB 12+.  Older GDB: set logging on
(gdb) bt full 25                      # on screen AND in the log
(gdb) pipe bt | wc -l                 # GDB 8.3+: pipe output to a shell command
(gdb) shell date                      # timestamp a finding in the log
(gdb) python print(gdb.execute("info threads", to_string=True))

Layer 2 · Repeatable script

(gdb) save breakpoints bp.gdb          # every break, watch, dprintf and condition
$ gdb -x bp.gdb --args ./app <args>    # next engineer replays your setup
$ gdb -batch -x trace.gdb ./app > run1.log 2>&1   # unattended run
# define your own shortcuts once
define where3
  bt 3
  info locals
end
document where3
Short backtrace plus locals.
end

A .gdbinit in the project directory is ignored unless you allow it: add set auto-load safe-path /path/to/project to your user ~/.gdbinit.

Layer 3 · Snapshots to hand off

(gdb) gcore state-at-fault.core         # core of the live process
(gdb) dump binary memory msg.bin <start> <end>   # raw bytes of a buffer
(gdb) info registers
(gdb) info sharedlibrary
(gdb) info proc mappings
$ ulimit -c unlimited                    # so the next crash leaves a core

A core file is useless without the exact binary that produced it. Record the git SHA, the compiler flags, and keep the unstripped binary beside it.

Handoff packet checklist

  • One-line symptom, expected versus actual
  • Exact command to reproduce, and how often it fails
  • Build: git SHA, compiler, flags, -g present
  • bp.gdb or trace.gdb that reproduces your observation
  • Log of the run plus bt full at the point of interest
  • Hypotheses you eliminated, and the observation that eliminated each
  • Root cause and the file:line where the fix belongs

Easier on the eyes

    
A better screen than the bare prompt

    
GDB ships a text user interface. If you want more than that, there are friendlier front ends.

  

  

    

      
Built-in TUI

      
$ gdb -tui ./app            # or inside GDB:  tui enable
(gdb) layout src            # source with the current line marked
(gdb) layout split          # source + assembly
(gdb) layout regs           # registers on top
(gdb) focus cmd             # keys go to the command line   (focus src to scroll code)
(gdb) refresh               # redraw if output smears   (or Ctrl-L)
(gdb) tui new-layout dbg src 2 cmd 1   # GDB 10+: your own layout

      
Ctrl-x a leaves or enters the TUI, Ctrl-x o switches the active window, Ctrl-x 1 and Ctrl-x 2 pick one or two windows, Ctrl-x s toggles single-key mode (n, s, c, and so on). Pressing Enter repeats the last command, which is how the video steps through a program.

(gdb) info pretty-printer          # are the STL printers loaded?
(gdb) p myVector                   # should show {size = 3, ...} not raw _M_impl
(gdb) set print object on
(gdb) set print static-members off
(gdb) set print frame-arguments all
(gdb) set print demangle on
(gdb) p dynamic_cast<Derived*>(basePtr)

Your target is not a laptop

    
Embedded and RTOS specifics

    
What changes when the program runs on a board, a simulator, or a Linux target. Check which of these applies to your project and skip the rest.

  

  

    

      
Connect and control

      
# on the target (Linux/RTOS with network):
target$ gdbserver :2345 ./app
host$   gdb ./app
(gdb) target remote 10.0.0.5:2345

# through a probe (OpenOCD shown):
(gdb) target extended-remote :3333
(gdb) monitor reset halt        # "monitor" passes text to the probe server
(gdb) load                      # flash the ELF
(gdb) continue
(gdb) set remote hardware-watchpoint-limit 4   # match your core's comparator count
(gdb) show can-use-hw-watchpoints

      
Always load the ELF built with -g on the host. The board runs the stripped image; GDB reads symbols from the file.

    

    

      
Optimized builds

      
If you see <optimized out>, rebuild the one file with -Og -g3, or the whole target with -O0 for the investigation.

      
$ gcc -Og -g3 -fno-omit-frame-pointer ...
(gdb) info macro MAX_MSGS          # works with -g3
(gdb) set substitute-path /build/ci/src /home/me/src   # sources moved since the build
(gdb) directory /home/me/src

    

    

      
RTOS awareness

      
With a probe that understands your RTOS (for example OpenOCD -rtos FreeRTOS), info threads lists tasks instead of one CPU context. Without it, read the kernel's own structures.

      
# FreeRTOS example. Names depend on your port and config.
(gdb) p pxCurrentTCB->pcTaskName
(gdb) p pxCurrentTCB->uxPriority
(gdb) p uxCurrentNumberOfTasks
(gdb) p xTickCount                  # your own timeline for deadlines
(gdb) x/64xw pxCurrentTCB->pxStack  # 0xa5a5a5a5 = stack never touched; count what remains

    

    

      
Cortex-M fault (if you are on ARM M-class)

      
(gdb) x/wx 0xE000ED28     # CFSR: which fault (memory, bus, usage)
(gdb) x/wx 0xE000ED2C     # HFSR
(gdb) x/wx 0xE000ED34     # MMFAR  (valid if CFSR says so)
(gdb) x/wx 0xE000ED38     # BFAR
(gdb) p/x $lr             # EXC_RETURN: bit 2 set = frame on PSP, clear = MSP
(gdb) x/8wx $psp          # stacked: r0 r1 r2 r3 r12 lr pc xpsr
(gdb) info symbol *(int*)($psp+24)   # stacked PC = the faulting instruction

    

    

      Halting changes time. While the target is stopped, hardware timers may keep running and other peers keep talking. A timeout that fires right after you resume might be your breakpoint, not the bug. Use dprintf plus the system tick for timing questions, and trust the tick counter rather than wall-clock time.
