# 02 · What the authorities say, and the rule each became

Each row: **source → what it actually says (verified wording where in quotes) → the rule in this book.**

| Source | What it says | Rule in the book |
|---|---|---|
| **Pólya**, *How to Solve It* (1945) [S04] | Four phases: understand the problem, make a plan, carry out the plan, look back. "Understand" = identify the unknown, the data, and the condition linking them. (Wikipedia; question wording not checked against the book.) | The 7 steps keep Pólya's order. **Behavior Card = unknown / data / condition** in code terms. Step 7 "Log it" = "look back". |
| **Naur** (1985) [S01] | The programmer's *theory* lets them explain, justify, and "respond constructively to any demand for a modification". Changes made "without a proper grasp of the underlying theory" cause decay. | **Confidence Gate** (Explain / Predict / Locate) before any debugger work. |
| **Zeller**, *Why Programs Fail* ch. 6 [S02] | Scientific method for debugging: 1 observe a failure; 2 invent a hypothesis consistent with observations; 3 use it to make predictions; 4 test by experiment/observation (refine or replace); 5 repeat "until the hypothesis can no longer be refined". Chain: defect → infection → failure (infection = bad program *state*). | Steps 4–5 are this loop. Debugging = find the **first bad state** (the infection) and the write that made it. Every probe is an experiment with a stated prediction. |
| **Zeller** TRAFFIC [S02b] | Track, Reproduce, Automate, Find origins, Focus, Isolate, Correct. | Step 1 (reproduce + track), step 4 (automate probes as scripts), step 5 (find origins/focus/isolate), step 6 (correct + prove). |
| **Agans** (2002) [S03] | Nine rules: Understand the System; Make It Fail; Quit Thinking and Look; Divide and Conquer; Change One Thing at a Time; Keep an Audit Trail; Check the Plug; Get a Fresh View; If You Didn't Fix It, It Ain't Fixed. Quotes: "guess only to focus the search. You still have to confirm that your guess is correct by seeing the failure"; "write down what you did, what order you did it in, and what happened as a result"; "don't change the mechanism" when instrumenting. | Step 2 = rule 1; step 1 = rule 2; "look" = probes; journal = audit trail; step 6 = rule 9; the **stuck clock** = rule 8 (fresh view). Rule "don't change the mechanism" → prefer debugger probes over editing code with prints. |
| **Pike** (1989) [S05] | Rule 1: "You can't tell where a program is going to spend its time." Rule 2: "Don't tune for speed until you've measured…" Rule 5: "If you've chosen the right data structures and organized things well, the algorithms will almost always be self-evident." (cites Brooks) | **Data first.** The Card starts with data, not functions. Measure, don't guess. |
| **Brooks** (ch. 9) [S06], **Torvalds** (2006) [S07] | Brooks: show the tables (data) and the flowcharts become unnecessary (wording varies by edition — paraphrased only). Torvalds (git list, via LWN): good programmers "worry about data structures and their relationships". | Same as Pike: the *relationships between data* are the map. |
| **Lamport** [S08] | Think about the system "above the code": a specification/abstraction before code. TLA+ views a system as behaviors = sequences of states: an initial-state predicate, a next-state relation, and invariants. (Source: abstract + secondary TLA+ notes; his book PDF was unreadable to our fetcher.) | **State language.** A behavior is a sequence of states; a bug is a state that violates an invariant, or a transition that isn't taken. |
| **Hoare / Meyer** [S09] | {P} C {Q}: if P holds before C, Q holds after. Class invariants hold whenever an object is observable from outside. | **Declare·Define·Implement** maps to: Declare = the things in P/Q; Define = the predicates P, Q, invariant; Implement = C. Postcondition checks = conditional breakpoints at function exit. |
| **Feathers** [S10] | Characterization tests record what code *actually does*; a *seam* is a place you can change behavior without editing there. | Family C: before changing, characterize with a probe run; use the write/read log to find change points and seams. |
| **Google SRE ch. 12** [S11] | Troubleshooting as the "hypothetico-deductive method"; "compare the observed state of the system against our theories to find confirming or disconfirming evidence." Good problem report: "the *expected* behavior, the *actual* behavior, and, if possible, how to reproduce". Pitfalls: irrelevant symptoms, wrong hypotheses, "spurious correlations". Techniques: "Simplify and reduce", "bisection", "What touched it last". "Ask 'what,' 'where,' and 'why'". | The **Behavior Card's top two lines are SRE's problem report** (expected / actual / repro). Bisection and "what touched it last" are in the localize table. |
| **Ko & Myers** [S12] | Programmers ask "why did / why didn't" questions; 68% in their prior observation were why-didn't. | Type B2 recipe (break at the decision, show the guard operands). |
| **Alaboudi & LaToza** [S13] | Early correct hypothesis predicts success; people hold ~2 hypotheses per defect; offering fault locations didn't help, offering hypotheses did. | Hypothesis Ledger; "bring a hypothesis, not just a symptom" when asking for help. |
| **Shah & Croft-White** (2025) [S19] | Step 1 is run the program; anchor on `main`; "follow the data" instead of control flow; a watchpoint with a condition ("when does the profit go up") lets you "start exploring the codebase at that point"; "most of us don't get the luxury of four years to understand the codebase". | Step 1; follow-the-data probes; the slice rule in chapter 5. |
| **Beller et al.** [S14] | Experts: "once one knows the condition, one almost automatically understands the problem." | The thesis of the book. |

## Innovation (what we can and cannot claim)
- Claim we can support: **shorter loops from question to evidence mean more questions get asked.** Support is
  indirect: Victor's "Inventing on Principle" argues creators need an immediate connection to what they create
  (secondary sources only, S20); the Whyline study measured faster debugging with question-driven tooling (S12, small study).
- Claim we **cannot** support with evidence: "this method produces innovation." The book says: it removes the
  main obstacle to experimenting in unfamiliar code (fear and slowness), and leaves the ideas to you.
